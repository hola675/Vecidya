## Resumen ejecutivo

Vecidya Platform es una aplicación SSR de React Router sobre Cloudflare Workers, Better Auth, Drizzle ORM y D1. Cubre identidad, organizaciones, membresías, permisos, perfil comercial (uno por organización), servicios Vecidya, directorio público (Vecindario), Diagnóstico anónimo, administración interna con gobierno de perfiles y una web pública institucional. Vecidya **no es un CRM**: GHL es el system of record comercial y hoy no existe ninguna integración con GHL.

La superficie pública comercial mantiene un catálogo visual local en `public/assets/catalog/`, registrado por `app/assets/public-assets.ts`. Las páginas de Diagnóstico, Licencias, Addons y Servicios consumen los assets seleccionados; las etiquetas de acciones y las fronteras licencia/addon/servicio viven en `app/content/public-copy.ts` para evitar divergencias de copy. Esta integración no cambia el motor DIAG-V3 ni está publicada.

Publicado en `vecidya.com` (verificado HTTP el 2026-09-22 y autenticación histórica manual): la web pública completa y **un** perfil real (`/vecindario/vecidya`), ahora sobre `vecidya-prod`; migraciones `0000`–`0009` están presentes. EMAIL-001 añadió evidencia manual autorizada del flujo `forgot-password → Gmail real → enlace de producción → reset-password → contraseña modificada` para `hola@vecidya.com`; la autenticación posterior con la nueva contraseña no fue declarada sin evidencia separada.

Soportado y probado (`pe-b` pasa): un usuario puede pertenecer a varias organizaciones y ser owner de varias (`member` es único por `(organization_id, user_id)`, sin límite de organizaciones); cada organización tiene como máximo un `business_profile` (índice único por `organization_id`); `slug` es único global para perfiles y para organizaciones; `session.active_organization_id` selecciona el contexto y se inicializa con la primera membresía válida; al retirar membresía se limpian sesiones activas obsoletas; toda consulta tenant filtra por la organización verificada. `platform_member` es una tabla separada que nunca se deriva de `member.role`. Detalle de aislamiento en [DATABASE.md](DATABASE.md) y [ARCHITECTURE.md](ARCHITECTURE.md).

## Licenciamiento multi-negocio (LICENSE-STRATEGY-001, foundation, solo local)

1 organización = 1 negocio = 1 licencia; la cantidad de organizaciones no depende del plan de ninguna de ellas. `billing_account` (quien paga) es independiente de `member`: pertenecer a una organización (incluida una invitación aceptada) nunca hace que su licencia cuente para el portafolio de otra persona. Portafolio aprobado por el usuario: 1 organización sin descuento, 2 → 10%, 3-4 → 15%, 5+ → 20%, calculado en centavos enteros por `db/pricing/calculator.ts` (función pura, sin acceso a base de datos, 21 pruebas unitarias). Un cambio de plan cancela la licencia vigente y crea una nueva, conservando historial y sin afectar a otras organizaciones del mismo `billing_account`; el precio contratado (`price_id`) no se recalcula cuando cambia el precio de lista (grandfathering real). Solo `platform_admin` asigna, cambia, suspende/reactiva o transfiere una licencia (`/api/platform/organizations/:id/license`), auditado en `platform_audit_log`. No hay checkout, proveedor de cobro, UI de Admin ni entitlement enforcement todavía; la migración `0010` solo se aplicó en local. Detalle completo en [DATABASE.md](DATABASE.md#licenciamiento-multi-negocio-license-strategy-001).
